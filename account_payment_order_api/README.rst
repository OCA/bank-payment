Payment orders are usually exported as a file that someone uploads to the bank.
Many banks now take the same payments through an API, and answer for each
payment separately: some are accepted, some are refused, the accepted ones are
paid hours later, and a paid transfer can still come back.

This module adds that path to outbound payment orders:

* a payment mode gets a **Bank API Provider** (added by a provider module);
* **Send to Bank** creates one bank batch per kind of payment, reserves its
  number at the bank and records it before sending, so a timeout never leads to
  a second payment: an unknown outcome is checked at the bank, never sent again;
* each line keeps its own status (accepted, awaiting release, paid, refused,
  rejected, cancelled, returned) and the bank reason;
* the payment of a line is posted and reconciled only when the bank reports it
  as paid, with the payment date given by the bank; refused or rejected lines
  cancel their draft payment and the bill can be paid by another order right
  away; a returned payment is cancelled and the bill is open again.

This module contains no bank: provider modules implement the calls.

Usage
=====

#. Create an outbound payment order with a payment mode that has a Bank API
   Provider and add the bills as usual.
#. Confirm it. One draft payment is created per line; nothing is posted yet.
#. Click **Send to Bank**. The **Bank** tab shows the batches and the status of
   every line. If the bank requires the payments to be released (approved) on
   its own channel, do it there.
#. A scheduled action checks the batches every 10 minutes; **Check Bank Now**
   checks them at once. Paid lines are posted and reconciled, refused ones are
   freed, and the order is done when every line has a final status.
#. Lines the bank has not executed yet can be cancelled from the **Bank** tab.

With **Require Second Factor** on the payment mode, **Send to Bank** asks for a
code from the authenticator app of the user, who enables two-factor
authentication in the user profile. Each code works once and is recorded on the
order, and wrong codes lock the user out for a while. A company can also require,
in the Invoicing settings, that the user who enters the code is not the one who
confirmed the order. A payment mode without the option sends without the code.

Known issues / Roadmap
======================

* Webhooks: banks that notify status changes could update the lines without
  waiting for the scheduled check; providers can call the same update today.
* Releasing a batch from Odoo, for banks that allow it through the API.
* A provider must raise ``PaymentApiResultUnknown`` whenever the bank may have
  received a batch (timeout, connection lost); any other error marks the lines
  as refused.
* A provider action that moves money can require the same code: list its private
  method in ``_api_second_factor_methods`` on the model and return
  ``self.env["account.payment.api.second.factor"]._run_after_check(self, method)``.
